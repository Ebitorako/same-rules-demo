# 组员剧情接入指南

游戏名为 **Genderpoly**，游戏内公司名为 **FreeDOM**，注意保留这个大小写。游戏正文用英文，CSV 表头保留中文。剧情与代码分开：通常只需要把组员的定稿填进数据文件，再运行检查。规则依据是 [GAME_SPEC.md](GAME_SPEC.md)。

## 应该修改哪个文件

| 文件 | 用途 |
|---|---|
| [scenarios.csv](../public/data/scenarios.csv) | 场景、三选一选项、两种棋子的结果、NPC 表情、隐藏数值变化 |
| [endings.csv](../public/data/endings.csv) | 结局正面文字、背面理论与文献 |
| [guide.csv](../public/data/guide.csv) | 常驻引导 NPC 的选择前建议、行业背景、理论解释与对应文献 |
| [guide.json](../public/data/guide.json) | 引导 NPC 的名字、身份说明与头像资源名称 |
| [candidates.json](../public/data/candidates.json) | 第四章招聘的三位候选人 |
| [policies.json](../public/data/policies.json) | 政策名称、描述及是否属于当前 Demo 范围 |
| [copy.json](../public/data/copy.json) | `title` 为游戏名 Genderpoly，`companyName` 为棋盘中央公司名 FreeDOM；还包含角色介绍、晋升等共用叙事文字，以及可选的 `statDescriptions` 能力解释 |

最初收到的原表保存在 [starter-data/](starter-data/)，游戏只读取 `public/data/`。原始 `C2-03` 示例已接入当前剧情表，其余测试内容中的占位标记提醒团队继续替换。

## 情境表：一行是一个选项

同一卡牌通常有三行，分别对应选项 `1`、`2`、`3`。同一卡牌的卡号、章节、标题、场景描述、背景信息和 NPC 应重复保持一致。

保留这些卡号与位置：

| 章节 | 情境卡 | Boss 卡 |
|---|---|---|
| Ch1 | `C1-01` 至 `C1-04` | `C1-B` |
| Ch2 | `C2-01` 至 `C2-04` | `C2-B` |
| Ch3 | `C3-01` 至 `C3-05` | `C3-B` |
| Ch4 | `C4-01` 至 `C4-03` | `C4-B` |

共 20 张卡牌。Creative Director 是棋盘上的晋升位置，不另加一张普通情境卡。

“适用棋子”填写 `都可`、`仅♀` 或 `仅♂`。每个棋子在每张卡上都应恰好看到三个可选项。若选项 2 的文字不同，可参考 `C2-03`：用两行相同卡号和选项号，分别填 `仅♀`、`仅♂`。不能简单删掉某一棋子的一个选项，让它只剩两个。

同一个选择可以有两种结果：分别填写“结果 ♀”“结果 ♂”、“NPC 表情 ♀”“NPC 表情 ♂”、“数值变化 ♀”“数值变化 ♂”。仅限一种棋子的行，另一侧结果可以留空。空白“选项文字”的行会被跳过，不会成为游戏选项。

Boss 是否通过由实际隐藏数值与门槛决定，不能通过修改结果文字来改变。**Boss 检查失败时直接显示结局卡，不显示这张卡的结果页，也不需要再按 Continue。** 请把失败后的结局文字写在 `endings.csv` 对应结局中，不要把玩家必须读到的失败说明只放进 Boss 的“结果”单元格。数值默认值没有因此改变；The System 当前没有失败门槛，保持既有行为。

## 表情、数值和条件

NPC 表情使用表里的中文名称：

| 表格用词 | 图片文件名中的英文 |
|---|---|
| 满意 | `pleased` |
| 中性 | `neutral` |
| 打量 | `appraising` |
| 皱眉 | `frowning` |
| 尴尬 | `awkward` |
| 冷淡 | `cold` |

数值变化示例：`Network+1, Energy-1`。数值名称只能是以下八项，注意拼写：

`Creativity`、`Communication`、`Skill`、`Energy`、`Network`、`Reputation`、`Availability`、`Money`。

没有变化时可以留空。两种棋子开局使用相同数值；差异发生在工作环境的回应与要求中。不要为了表现性别差异，给两种棋子不同的初始能力。

v0.11 起，数值在游玩和 **YOUR CHOICES** 日常回顾中仍隐藏，只在职业结束后揭示。表中的“数值变化”是选项要求的增减，游戏仍按原有上下限执行；结局复盘会区分要求与实际变化。例如原值 9、要求 `+3`、上限 10，实际变化为 `+1`。不要为了让复盘数字相等而改动剧情表或限值。

“出现条件（可选）”为空表示没有额外条件。目前支持：

| 写法 | 意思 |
|---|---|
| `C1-02=2` | 本轮在 C1-02 选择了选项 2 |
| `policy:formal_recruitment` | 本轮启用了上一轮制定的正式招聘政策 |
| `round>=2` | 第二轮或以后 |
| `round>=2;policy:formal_recruitment` | 两个条件都满足 |

条件会影响实际可用选项。新增有条件的分支时，必须给未满足条件的路径留下完整的三个选项，并请 Codex 一起检查；不要自行添加新的条件语法。相同条件下同一棋子的同一选项号也不能重复出现。

## 第四章、政策与下一轮

第四章的前提是通过 **The Ideal Worker**，到达 **Creative Director** 格并经历晋升场景。未通过这位 Boss 会直接进入结局，不能继续到招聘或政策卡。晋升场景文字仍在 `copy.json` 的 `promotionTitle`、`promotionText` 中填写；不要把晋升说明移到第四章卡牌里而省略原场景。

候选人 JSON 中：`id` 是程序识别用的编号，`name` 是名字，`pawn` 使用 `female` 或 `male`，`blurb` 是人物介绍。`stats` 用于描述候选人资料，**不会把这些数值直接带入下一轮开局**；下一轮仍按统一的初始数值开始，延续“同样的起点”。

候选人和第四章招聘卡 `C4-01` 的三个选项需要一一对应：当前选项 1 对应 `cand_a`，选项 2 对应 `cand_b`，选项 3 对应 `cand_c`。修改名字后检查候选人文件与卡牌文字一致；若改变编号或招聘对应关系，请让 Codex 同步调整 `src/config/rules.ts`。

政策 JSON 中的 `name`、`benefit`、`cost`、`nextRoundEffect` 是文字说明；只改一句描述不会自动产生新的规则效果。当前 `C4-02` 的选项 1 对应 `formal_recruitment`：它取消下一轮 Gatekeeper 的隐藏“fit”惩罚。其他政策仍是待讨论项目，不能仅把 `mvp` 改为 `true` 就当作已经实现。

## 结局与背景理论

结局表的“触发条件”是方便团队阅读的说明。实际的优先级、门槛和判定由程序执行。改结局文字可直接改表；新增结局编号或改触发条件时，需要同步修改规则并测试。结局图片的命名见[美术指南](ART_GUIDE.zh-CN.md)。

当前六个结局按退出原因（倦怠或前三位 Boss 未通过），或完整职业结束时是否推行正式招聘政策来选择。规格提出 The System 的最后选择应影响结局，但三个选项与结局的具体对应关系尚未由团队定义，当前骨架尚未把这最后一次选择设为独立的结局分支。请先确定这个对应关系，再由 Codex 接入；不要只改结局表的“触发条件”就认为规则已生效。

剧情卡的“背景信息（游戏内可翻看）”保留原来的背景说明；没有填写独立引导内容时，引导 NPC 也可以展示这段说明及该卡的“对应文献”。“备注”仍只供团队使用。

结局卡和 Gallery 里已解锁的卡翻到背面后，分别显示 **Theory** 与 **References**。在 `endings.csv` 的“背面：理论概念”填写理论解释，在“对应文献”填写支持该解释的文献。可以在同一个单元格内换行列出多条引用；长内容会在卡背阅读区滚动。空引用会显示尚未填写的提示，程序不会代写或推测文献。不要把未经确认的占位解释当成最终论述。

v0.11 的结局卡正面在正文下增加八项最终能力值；背面在 Theory / References 后增加该职业的逐次选择与数值复盘。Gallery 按职业局数分别保留报告；旧存档缺少精确记录时会注明缺失或重建，不能把其他局的数据拿来填补。正文与理论仍照常写在 `endings.csv`，不需要把运行时的分数手填进剧情。

八项能力的解释在 `copy.json` 的可选 `statDescriptions` 对象中填写，保留上文八个英文能力名作为键，只编辑对应的说明文字。说明用于解释界面中的能力含义，不会修改数值或规则，也不属于正式理论或文献。组员仍需自行审阅、填写剧情和学术解释；不要在引导建议、普通选项或结果文字中提前泄露数值。

## 常驻引导 NPC：填写 guide.csv

引导 NPC 在桌面棋盘旁、窄屏棋盘下方显示。在情境卡或 Boss 卡上，建议出现在选择按钮之前，不会阻止玩家直接选择。玩家可以点击 **Hide advice** 收起、**Ask the guide** 恢复，点击 **Open the rulebook** 查看已有的行业背景、理论和文献。隐藏偏好会记住；旧存档缺少这项偏好时默认显示。阅读、隐藏建议不会改变数值、选项结果或结局。

`guide.csv` 的模板共 **22 行**：一行 `GENERAL`、一行 `PROMOTION`，以及前面列出的 20 个情境/Boss 卡号。这里是**每个卡号一行**，不要像 `scenarios.csv` 一样为三个选项重复三行。

| 列名 | 怎样填写 |
|---|---|
| 卡号 | 保留现有编号；`GENERAL` 为通用操作指引，`PROMOTION` 为晋升场景 |
| 选择前建议 | NPC 在选择之前说的话；`GENERAL` 这一格必须填写，其他行可留空 |
| 行业背景 | 这张卡涉及的行业情况或制度背景 |
| 理论解释 | 团队要传达的理论解释，和实际情境相联系 |
| 对应文献 | 支持本行背景与理论的文献；允许在单元格内换行 |
| 备注 | 分工、修改记录等，只供组员使用 |

目前只有 `GENERAL` 的导航提示；`PROMOTION` 和每张卡的专属台词、理论与文献仍留空，等组员定稿。程序不会自动创作这些内容。

填表时按这个顺序进行：

1. 找到卡号对应的行，先写“选择前建议”。提供理解情境的线索，让玩家自己决定，不要泄露隐藏数值或直接报出某选项的结果。留空则显示 `GENERAL` 的建议。
2. 决定是否沿用原剧情卡的解释。“行业背景”和“理论解释”**都留空**时，选择卡会沿用 `scenarios.csv` 当前卡的背景；“对应文献”未单独填写时也沿用该剧情卡的文献。
3. 如果开始填写独立的“行业背景”或“理论解释”，请在这一行自己填写支持它的“对应文献”。只要这两列任一有内容，程序就不会自动借用原剧情卡的引用，避免让旧文献看起来支持新的论断。
4. 一张卡只保留一行，不要改动六个表头，不要把 `GENERAL` 的建议删空。`PROMOTION` 的建议可以单独写；留空仍使用通用建议。
5. 导出 **CSV UTF-8**，替换 `public/data/guide.csv`。执行 `npm run validate-data`，再启动游戏，进入对应卡，检查选择前建议、展开的规则册和原来的三个选项。

NPC 的名字和身份说明在 `guide.json` 的 `name`、`role` 中修改。`portrait` 当前为 `npc/guide_neutral`，不带扩展名；它对应资源路径表中的固定名称。头像文件放在 `public/assets/npc/guide_neutral.svg`、`.png` 或 `.webp`，具体操作见[美术指南](ART_GUIDE.zh-CN.md)。

## 安全导出与检查

1. 保留原表备份。列名不要改，卡号和编号不要改成日期或数字。
2. Google Sheets 每个工作表分别下载为 CSV，替换对应文件。使用 Excel 时，将卡号、选项和条件等列作为文本导入，并选择 **CSV UTF-8** 保存，避免乱码、日期自动转换或科学计数法。
3. 不要把 `.xlsx` 改后缀伪装成 `.csv`。用表格软件导出，软件会处理正文里的逗号、引号和换行。
4. 双击根目录的 `检查项目.cmd`，或运行 `npm run validate-data`。根据提示修复数据，再运行 `npm test` 与 `npm run build`。
5. 启动游戏。用两种棋子分别看改动卡的三个选项、结果、表情、引导建议和背景；结局内容有改动时检查正面的八项能力值，以及卡背 Theory / References、逐次选择复盘与长文滚动。确认游玩和日常回顾仍隐藏数值；开发时需要提前核对可用 `?debug=1`，对外演示前去掉。

校验通过说明数据格式和被检查的规则可用，不代表理论准确、文字已校对或所有故事路径已经试玩。正式版交付前删除占位标记，确认所有内容由团队审阅。
